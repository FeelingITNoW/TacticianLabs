# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tactician Labs is a TFT (Teamfight Tactics) analytics platform, inspired by tactics.tools. The roadmap is in `.github/prompts/plan-tacticianLabs.prompt.md`. It has three loosely coupled parts:

1. **Airflow (Astronomer) ETL**: `dags/` + `include/`. It pulls high-elo matches from the Riot API, archives the raw JSON to Google Cloud Storage (GCS), and parses the matches into **BigQuery** (dataset `tft`), embedding each participant's comp with Gemini into a `REPEATED FLOAT64` column. Each ingest write also adds its matches to per-patch counter tables (see Stats below), which views turn into win, top-4, average-placement and play rates.
2. **BigQuery** is the relational store. Tables are defined in Terraform (`infra/gcp/bigquery.tf`, column layouts in `infra/gcp/bigquery/<table>.json`); there are no SQL migrations. Change a table by editing its JSON and applying Terraform.
3. **Frontend**: `src/` is TanStack Start + React + Vite + Tailwind v4 + shadcn/ui (port 3000). It reads BigQuery through server functions (see Frontend below). Routes: `/compositions` (the front page), `/units` with an itemization section per unit (best items, duos, trios), `/items` (Completed, Artifacts, Radiant, Emblems, Misc), `/leaderboard`, `/ask` (chat with the SQL agent) and a skeleton-only `/explorer`. `src/routeTree.gen.ts` is generated, so don't edit it by hand, but commit it after adding a route (CI checks it).

`infra/gcp/` is the live Terraform root: it provisions the GCS bucket (`google_storage_bucket.tft_match_data`), the BigQuery datasets and tables, plus everything to run ingestion as a Cloud Run Job in production (`include/jobs/ingest_matches.py`, image `Dockerfile.jobs`, deps `requirements-jobs.txt`), built by `cloudbuild.yaml` from a Developer Connect trigger and started daily by Cloud Scheduler. See `infra/gcp/README.md`. `main.py` is a placeholder.

## Commands

Airflow runs through the Astro CLI in Docker (`Dockerfile` = Astro Runtime 3.1, Python 3.12 inside the container):
- `astro dev start` / `astro dev restart`: Airflow UI at http://localhost:8080
- `astro dev pytest`: runs `tests/` inside the Airflow container (this is how `pytest.log` was produced)
- `astro dev pytest tests/dags/test_ingest_matches_to_gcs_and_bigquery.py -- -k TestParseMatchData`: run a single test/class
- `astro dev parse`: DAG integrity check (uses `.astro/test_dag_integrity_default.py`, don't edit it)

BigQuery:
- `cd infra/gcp && terraform apply`: create/alter datasets and tables
- `PYTHONPATH=include python -m db.seed_default_data [--skip-embeddings] [--limit N]`: the default dataset. It seeds Set 18 reference data, then loads the matches archived under `tft/matches/16.19.1/2026-09-28/` in GCS. Idempotent, so it doubles as a reset.
- `PYTHONPATH=include python -m jobs.rebuild_stats [--check] [--table NAME ...] [--patch X|latest]`: recompute the totals tables from the match tables, or (with `--check`) report any that disagree with a recount. `--table`/`--patch` limit it to some tables and one patch, which only reads that patch's days (e.g. `--table champion_item_pair_totals --patch latest` backfills a new table for the current patch)
- `PYTHONPATH=include python -m jobs.backfill_names [--table participant_units|unit_items|participants]`: fill `participant_units.champion_name`/`unit_items.item_name`, and `participants.completed_items`/`board_cost`, from the reference tables for rows already stored (the ingest fills them as it writes, and `db.seed_reference_data` runs this after every reseed). Scans the whole tables, rewrites only missing or stale values
- `PYTHONPATH=include python -m jobs.cluster_compositions [--patch X] [--dry-run] [--min-cluster-size N]`: cluster a patch's boards into comps (see Compositions below); `--dry-run` prints them and writes nothing
- `PYTHONPATH=include python -m insights.nl_to_sql "which champions have the best top 4 rate"`: ask the stats views a question in plain English; Gemini writes the SQL (needs `GEMINI_API_KEY` and `GEMINI_SQL_MODEL`, the model that writes it) and the output ends with the SQL it ran
- `PYTHONPATH=include python -m insights.server`: the HTTP service (`POST /ask`, `GET /healthz`, `AGENT_HOST`/`AGENT_PORT`, default 127.0.0.1:8001) the web app's `/ask` page calls; the app finds it through `AGENT_URL`. Needs the same env as `nl_to_sql`
- `PYTHONPATH=include python -m db.seed_reference_data`: only `champions`/`traits`/`items`, from the `tft-*.json` files in `include/db/reference_data/` (Data Dragon 16.19.1), then refreshes the stored names via `jobs.backfill_names`
- `PYTHONPATH=include python -m jobs.load_gcs_matches --prefix tft/matches/<version>/<date>/ [--reload] [--skip-embeddings]`: load any archived day into BigQuery; skips matches already loaded
- Local runs use Application Default Credentials (`gcloud auth application-default login`); set `GOOGLE_CLOUD_PROJECT`, and `BQ_DATASET` if it isn't `tft`

Frontend: `npm run dev` (or `docker compose up`, which uses `Dockerfile.node` and mounts your gcloud credentials), `npm run build`, `npm run typecheck`. The server functions read BigQuery with your Application Default Credentials: set `GOOGLE_CLOUD_PROJECT` (`GCP_PROJECT_ID`, already in `.env`, also works), and optionally `BQ_DATASET` (default `tft`) and `BQ_LOCATION` (default `us-central1`). Never point it at the data-editor service account. There is no JS test or lint setup. Production: `npm run build` then `npm start` (`server.mjs`: serves `dist/client` plus the Start handler on `$PORT`, `/healthz` for health checks). Railway builds `Dockerfile.web` (see `railway.json`); with no gcloud there, set `GOOGLE_CREDENTIALS_JSON` to a read-only (BigQuery Data Viewer + Job User) service account key, plus `GOOGLE_CLOUD_PROJECT`, and `AGENT_URL` for `/ask`. The agent is a second Railway service built from `Dockerfile.agent` (`railway.agent.json`, deps in `requirements-agent.txt`): it binds `$PORT` (`AGENT_HOST=::` in the image), reads `GOOGLE_CREDENTIALS_JSON` too, and must stay off the public internet since it has no login.

Host-side Python uses uv (`pyproject.toml`, Python 3.14, deps in the `dev` group): `uv sync`, `uv run pytest ...`. Note that the tests import Airflow, which is only installed in the Astro container.

## Architecture notes

**Import paths.** DAGs import from `include/` as top-level packages (`from riot_api.match_api import ...`, `from db.parse_match_data import ...`). This works because the `Dockerfile` adds `/usr/local/airflow/include` to `PYTHONPATH` and `pyproject.toml` sets pytest `pythonpath = [".", "include", "dags"]`. Keep using this style, not `include.x`.

**Dependencies live in four places:** `requirements.txt` (Astro/Airflow image), `requirements-jobs.txt` (Cloud Run job image), `pyproject.toml` (uv host env), and `requirements-data.txt` (the Node dev container). Add Airflow-runtime deps to `requirements.txt`, and to `requirements-jobs.txt` too if `include/` code used by the job needs them.

**`ingest_matches_to_gcs_and_bigquery` DAG (daily):**
`collect_match_ids_task.expand(platforms=routing_groups().values())` (one task per routing region) → `collect_matches_task` → fans out to `upload_to_gcs_task` (key `tft/matches/{ddragon_version}/{utc_date}/{match_id}.json`) and `upsert_to_bigquery_task`. `upsert_players_task` runs before the DB upsert. Both DAGs reach BigQuery through `BigQueryHook(gcp_conn_id="google_cloud_default").get_client()`. Tasks are `async` and use `httpx.AsyncClient`. The Riot fetch tasks run with `max_active_tis_per_dagrun=1` to respect rate limits.

**Riot API (`include/riot_api/`).** This is the canonical client. `constants.py` has the regions, the platform→routing map (`RIOT_REGIONS_MAP`) and `HIGH_ELO_TIERS` (Challenger, Grandmaster and Master). Master is ~28k players across `RIOT_REGIONS` and each crawled player costs one sequential match-history request, so `collect_match_ids` crawls per routing region in priority order: every Challenger on the region's platforms, then every Grandmaster (both always in full), then Masters (round-robin by LP rank across the platforms, `MASTER_CRAWL_BATCH` players at a time) until `ROUTING_MATCH_TARGET` (2000) *new* matches are found. It takes a `filter_new` callback (the ingest passes `filter_new_match_ids`) so matches already stored or rejected don't count; `upsert_players` still stores every Master. `collect_match_ids` returns the new matches in priority order as `{match_id: [tiers whose players had it]}`; `TIER_QUEUES` in `constants.py` says which queues a tier may record (ranked 1100 from any tier, normal 1090 only from Challengers, nothing else), and `allowed_queues` takes the union over a match's tiers. League endpoints use the platform (`NA1`), match endpoints use the routing region (`AMERICAS`). Use `riot_get_with_retry` (429/backoff). `riot_data_retrieval.py` is only a re-export shim. `league_api.get_league_entries` returns the full apex-tier list; `include/db/upsert_players.py` builds `players`/`player_ranked_stats` rows straight from it (no per-player calls) and MERGEs them. Riot dev keys expire every 24h, so scheduled runs need a Personal key.

**BigQuery writes (`include/db/bq.py`).** Every writer stages rows into fresh tables in the `tft_staging` dataset with load jobs (free; tables expire after a day), then moves them, and updates the stats counters, with one transaction script, via `run_query`/`with_retry` (retries 5xx and concurrent-DML aborts, with jitter, since parallel tasks MERGE into the same totals rows). Primary and foreign keys are declared `NOT ENFORCED`; the writers keep them true. Every per-match table carries `played_at` and is day-partitioned on it.

**Parsing (`include/db/parse_match_data.py`).** `build_match_rows` is pure apart from the Gemini call: it skips any queue outside its `queues` argument (ranked, `queue_id` 1100, by default) and leaves out bots (every bot in a normal lobby has the puuid `BOT`, which would break the `(match_id, puuid)` key), and returns rows keyed by table for `matches`, `players`, `participants` (with a 768-dim `gemini-embedding-001` embedding of the board's units with star level and all items, plus traits, one batched `get_embeddings` call per match), `participant_traits`, `participant_units` (keyed on `slot`, the unit's index on the board, so duplicate champions survive) and `unit_items`. Riot payloads only carry api names, so `participant_units.champion_name` and `unit_items.item_name` are not in the parsed rows: `write_match_rows` inserts those two tables with `db.reference_names.insert_with_names_sql`, which LEFT JOINs the staging rows to `champions`/`items` (NULL when the api name isn't seeded), and `jobs.backfill_names` refreshes stored rows. `participants.completed_items` (items on the board whose `items.item_type` isn't component) and `participants.board_cost` (sum of `champions.cost * 3^(star - 1)`, the gold the units are worth) work the same way: `db.board_summary.insert_participants_sql` computes them from the staged units and items as participants are inserted, and `jobs.backfill_names --table participants` recounts stored rows. `write_matches` parses a batch and `write_match_rows` replaces those matches in one script: delete `matches` first, delete-then-insert each child table, MERGE `players`, insert `matches` last, so a crash part-way leaves the match absent and it is re-ingested. `filter_new_match_ids` skips already-ingested matches, and matches in `rejected_matches`, before fetching. `select_matches` splits a fetched chunk into the matches to record and the rejected ones (by `allowed_queues` for the tiers that surfaced each); `write_rejected_matches` MERGEs the latter into `rejected_matches` so no later run requests them again, and only the recorded ones are archived to GCS. `build_match_rows`/`write_matches` take a `queues` set (ranked only by default, `INGEST_QUEUES` from the ingest); `load_gcs_matches` stays ranked-only unless `--include-normals`.

**Stats (`include/data_aggregation/` + views).** Stats count ranked matches only (`counts_sql` filters `matches.queue_id = 1100`), since the match tables also hold Challengers' normal games, and so does the comp clustering. Stats are exact integer counters, summed per patch (`patch` is `matches.game_version`), in `patch_totals`, `champion_totals`, `trait_totals`, `item_totals`, `champion_item_totals`, `champion_item_pair_totals` (two items on the same unit, stored once as `item_a <= item_b`) and `champion_item_trio_totals` (a unit holding exactly three items, `item_a <= item_b <= item_c`), each with boards, matches, placement sum, top-4 and win counts. `patch_totals` carries the same placement sum, top-4 and win counts over all the patch's boards, the baseline for the deltas below (rows written before those columns existed hold NULL until `jobs.rebuild_stats --table patch_totals`). `write_match_rows` folds each write's matches into them with one MERGE per table, in the same transaction as the match inserts, so nothing is re-scanned. Each MERGE adds the staged rows' counts and subtracts the rows being replaced, so reloads and overlapping re-ingests never double count, and a match moves patch cleanly. A board counts once per entity however many copies it holds, and only active traits (`tier_current > 0`) count. The `composition_star_totals` (each unit's star level, its best copy's), `composition_completed_item_totals`, `composition_board_cost_totals` and `composition_trait_totals` (active traits by tier) count a comp's boards the same way, but by the comp each board was assigned to, which only the clustering job knows: they are `Totals(clustered=True)`, never merged by ingest writes (`INGEST_TOTALS` are), and `write_compositions` rebuilds the patch's rows (`COMPOSITION_TOTALS`) in the transaction that writes the comps. **Deltas** (how many places having something is worth) are views over those counters, never stored: the "without" group is the superset's counters minus the entity's (all boards for units, traits and items from `patch_totals`; the champion's boards for a unit's item from `champion_totals`; the comp's boards from `compositions` for units and traits in a comp), so they are exact. `delta = average_placement - the baseline's average placement` (negative = having it is better; the baseline is all boards of the superset, including the entity's own), next to `games_without` and `win_rate_without`/`top4_rate_without`/`average_placement_without`. They are columns of `champion_stats`, `trait_stats`, `item_stats` and `champion_item_stats` (and the `current_*` views), plus `composition_unit_stats` and `composition_trait_stats` (one row per comp and unit/trait; `current_*` variants). Rates are never stored: the views `champion_stats`, `trait_stats`, `item_stats`, `champion_item_stats`, `champion_item_pair_stats` and `champion_item_trio_stats` derive them (`SAFE_DIVIDE`), where `play_rate` is boards per match that had the entity (1 to 8) and `frequency` is boards per match in the patch (0 to 8). `current_*_stats` views (also in `infra/gcp/bigquery/views/`) are the latest patch only, joined to names, and are what LLM and frontend queries should read. The `calculate_tft_stats` DAG has no schedule; it and `python -m jobs.rebuild_stats` rebuild every totals table from the match tables (first backfill, recovery), and `jobs.rebuild_stats --check` diffs the totals against a recount. The web app still reads 3-item builds from the `champion_item_trios` table function (`infra/gcp/bigquery/routines/`, arguments `p_*`), which counts them from the match tables on demand; pass it the patch's first and last ranked `played_at` (`patch_window`), or it scans the whole history instead of ~1 GB. Reference tables `champions`/`traits`/`items` have no patch column: they are keyed on Riot's api name (e.g. `TFT_Item_BFSword`) and filled by `include/db/seed_reference_data.py`, which upserts and never deletes, so names resolve for old patches. `items.item_type` (artifact, radiant, component, emblem, misc or completed) is derived from the api name by `seed_reference_data.item_type`, since Data Dragon has no item category, and the `current_*item*` views expose it; misc is boosters, potions, consumables, chests, Masterwork Upgrade and Reforger, completed is every other item. `champions`/`traits`/`items` also carry an `image` path (`<ddragon version>/img/<group>/<file>`, relative to `https://ddragon.leagueoflegends.com/cdn/`), since file names can't be derived from api names (champion art is a ~500 KB splash). Set 18 api names start with `DA_` (e.g. `DA_18_KhaZix`, `DA_ArchangelsStaff`), which is what the seed filters on; update `TFT_SET`/`SET_ID_PREFIX` and the `tft-*.json` files in `include/db/reference_data/` for a new set.

**Compositions (`include/data_aggregation/compositions.py`).** Boards are grouped into comps from hand-built vectors, not the Gemini embedding (which stays for similarity search). A board's vector has a `u:<champion>` column of `(UNIT_BASE_WEIGHT + items held) * STAR_WEIGHTS[star]` (so itemized, starred-up carries and tanks dominate and itemless 1-star filler barely counts; duplicate copies take the max) and a `t:<trait>` column of `tier_current` (active traits only), L2-normalised. Only the clustering vectors use these weights; `avg_items` and the other stats read the raw `1 + items` counts. `jobs.cluster_compositions` fits HDBSCAN on a 50k-board sample of the patch (smallest comp: `MIN_CLUSTER_FRACTION` of the sample, at least 25 boards) (no number of comps to choose), drops clusters whose own boards are not alike (`MIN_COHESION`), then assigns every board to its nearest comp or leaves it out if it is less similar than the 20th percentile of that comp's sampled boards (`THRESHOLD_PERCENTILE`). It replaces the patch's rows in `compositions` (exact counters like `*_totals`, plus units, traits and carries as REPEATED records, and a `comp_id` hashed from the core units and carries so it survives reruns) and `participant_compositions`, in one transaction, and writes nothing if no comps are found. It is a separate Cloud Run Job (`tft-cluster-compositions`, same image, daily after the ingest) because it needs the whole patch. Each comp also gets a `category` (`compositions.categorize`, from `champions.cost` and the units' `avg_star`): carries of cost 1-3 averaging `REROLL_STAR` (2.5) or more make it a `1_cost_reroll`/`2_cost_reroll`/`3_cost_reroll` (the cost with the most such carries); otherwise `fast_9` when more carries are 5 costs than 4 costs, else `fast_8`; NULL when no carry has a known cost. `composition_stats` and `current_composition_stats` are the views to read; `composition_star_upgrade_stats` (what each one-star upgrade of a comp's units is worth: 1★→2★, and 2★→3★ for 1-3 costs only), `composition_completed_item_stats` and `composition_board_cost_stats` (both from the shared `composition_board_stats.sql.tftpl`) and their `current_*` views read the comp totals. Each comp is then split into variants (`find_variants`): the same HDBSCAN fit on that comp's boards alone (`MIN_VARIANT_SIZE`, `VARIANT_FRACTION`), keeping the sub-clusters that differ from the comp by at least one and at most `VARIANT_MAX_UNIT_DIFF` units, where a unit or trait differs when its frequency moves by `VARIANT_MIN_DIFF` (0.3). They go in `composition_variants` (exact counters like `compositions`, the comp's `comp_id`, a `variant_id` hashed from the comp and its added/removed units, and a `diff` list of what each variant adds or drops), and `participant_compositions.variant_id` says which one a board fits (NULL for the comp's base build, which is in no variant row). They are written in the same transaction as the comps; `composition_variant_stats` and `current_composition_variant_stats` are the views to read. `dags/cluster_compositions.py` is the unscheduled local equivalent. Tune `--min-cluster-size` with `--dry-run` on real data before trusting the comps.

**Leaderboard (`leaderboard` view).** Joins `player_ranked_stats` to `players` for the apex ladder. Rows are never deleted when a player leaves the apex tiers, but each platform is written by one MERGE, so the view drops rows more than 6 hours older than their platform's newest (`region_refreshed_at`). It adds `tier_order` and `region_rank`. Names are NULL until the player appears in an ingested match (~78% have one). Riot's league `wins` are top-4 finishes and `losses` the rest, so `wins / (wins + losses)` is a top-4 rate.

**Insights (`include/insights/`).** `nl_to_sql.ask` answers stats questions by giving Gemini one tool, `run_sql`, over the `current_*` views in `prompt.VIEWS`. Every one but `current_matches` and `current_participant_compositions` reads precomputed counters (3-item builds, comps' star upgrades, completed items and board costs included), so most questions bill kilobytes; add a counters table and view rather than a tool that reads the match tables. `run_sql` dry-runs each query first and refuses anything that isn't a single SELECT over `prompt.VIEWS`, or that would bill over `MAX_BYTES_BILLED`; errors go back to the model as the tool result so it can retry. The text the model reads (rules, column glossary, example queries) is in `insights/prompt.py`; `build_context` adds each view's live columns from `INFORMATION_SCHEMA`. Run it with a read-only identity once it is served to users. `ask` takes the earlier turns as `history` (last `MAX_HISTORY_TURNS`, text only) so follow-ups work; `insights/server.py` validates input, returns only `{text, queries}` and a generic error on failure. Its tests use no fixtures, so `pytest --noconftest tests/insights` runs them on the host without Airflow.

**Frontend (`src/`).** Server functions are the API: no HTTP service sits between the pages and BigQuery. `src/server/*.server.ts` holds the SQL, the BigQuery client (`bigquery.server.ts`: parameterized queries only, a `maximumBytesBilled` cap, job label `app=tactician-labs-web`, errors logged and rethrown without the SQL), an in-memory promise cache (`cache.server.ts`, so identical in-flight requests share one query) and row-to-DTO mapping; each starts with `import '@tanstack/react-start/server-only'` and the build fails if one reaches the client bundle. `src/data/*.functions.ts` are the `createServerFn` wrappers the routes call (they `import()` the server module inside the handler); `src/data/types.ts` has the DTOs. Pages read the `current_*` views, `leaderboard` and `champion_item_trios`, never the match tables directly, and validate route ids against the cached reference tables (`reference.server.ts`) before querying. Filters and sorts live in the URL: each route's zod `validateSearch` uses `.default(x).catch(x)` (the `.default` keeps the param optional on `<Link>`) plus `stripSearchParams(defaults)`, so bare URLs stay clean instead of redirecting. Small datasets are fetched once and filtered in the browser; the ~38k-player ladder is cached for 15 min and paged in memory. Trios are only requested when the Trios tab is open. `/ask` renders the agent's markdown with `react-markdown` + `remark-gfm` (no raw HTML); `lib/entity-matcher.ts` and `lib/remark-entities.ts` turn unit, item and trait names (and api names) in the text into `GameIcon`s. `src/server/agent.server.ts` calls the Python service over HTTP. The explorer has no backend: `src/data/explorer.ts` holds just the request/response contract and the page's Run button is disabled.

**Config/secrets.** DAGs read `GEMINI_API_KEY` and `RIOT_API_KEY` (or `API_KEY`) from `.env` (`GEMINI_API_KEY` isn't needed with `SKIP_EMBEDDINGS=1`, which `make_genai_client` honours: ingest then writes boards with no embedding and never calls Gemini. The Cloud Run ingest job sets it by default via the Terraform variable `skip_embeddings`; backfill later with `jobs.load_gcs_matches --reload`), plus optional `BQ_DATASET`/`BQ_STAGING_DATASET` (default `tft`/`tft_staging`). GCS and BigQuery are both accessed through the Airflow connection `google_cloud_default`, defined in `airflow_settings.yaml` (gitignored) with a service account keyfile; that account needs BigQuery Job User on the project and Data Editor on both datasets. The Cloud Run job instead uses its runtime service account's default credentials (granted in `infra/gcp/bigquery.tf`), no key needed.

**Tests.** `tests/conftest.py` points Airflow at a SQLite metadata DB and runs `initdb` once per session. Its `fake_bq` fixture (`FakeBigQuery`) records loads and queries instead of running them and checks every loaded row against the Terraform schema JSON, so a row/table mismatch fails a unit test. `tests/dags/test_constants.py` holds full sample Riot match payloads (ranked and unranked) for parser tests. `tests/dags/test_dag_example.py` asserts that every DAG imports cleanly and has tags and retries.

**CI (`.github/workflows/`).** `lint.yml` runs `ruff check`, and for the frontend `tsc --noEmit`, `npm run build` and a check that the committed `src/routeTree.gen.ts` matches the routes. Ruff is pinned to `0.15.9` (both in the workflow and as a dev dependency) with an explicit `[tool.ruff.lint] select` matching ruff's own conservative defaults (`E4`, `E7`, `E9`, `F`) — without that, a version bump (or `ruff-action` falling back to "latest" when it can't detect a pin) pulls in a much larger ruleset (isort, pylint, flake8-datetimez, ...) this codebase was never written against. `tests.yml` builds the `Dockerfile` image and runs `pytest tests -m "not integration"` inside it, with dummy `GEMINI_API_KEY`/`RIOT_API_KEY` values (the parsing tests patch `get_embeddings` and never call Riot, and BigQuery is faked). Tests marked `@pytest.mark.integration` hit live services and are excluded in CI: `TestCollectMatchIds` (Riot API) and `TestTotalsSqlCompiles` (dry-runs the totals SQL against real BigQuery; run it after `terraform apply`) and `TestBoardsSqlCompiles` (the same for the comps' boards query).
