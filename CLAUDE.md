# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A TFT (Teamfight Tactics) analytics pipeline, heading toward a tactics.tools clone. The roadmap is in `.github/prompts/plan-tacticsToolsClone.prompt.md`. It has three loosely coupled parts:

1. **Airflow (Astronomer) ETL**: `dags/` + `include/`. It pulls high-elo matches from the Riot API, archives the raw JSON to Google Cloud Storage (GCS), and parses the matches into **BigQuery** (dataset `tft`), embedding each participant's comp with Gemini into a `REPEATED FLOAT64` column. Each ingest write also adds its matches to per-patch counter tables (see Stats below), which views turn into win, top-4, average-placement and play rates.
2. **BigQuery** is the relational store. Tables are defined in Terraform (`infra/gcp/bigquery.tf`, column layouts in `infra/gcp/bigquery/<table>.json`); there are no SQL migrations. Change a table by editing its JSON and applying Terraform.
3. **Frontend**: `src/` is TanStack Start + React + Vite (port 3000). It's early: one `/leaderboard` route. It still queries **Supabase** directly, which no longer receives new data. `supabase/` (old migrations, `seed.sql`, local config) is kept only until the frontend moves to BigQuery. `src/routeTree.gen.ts` is generated, so don't edit it by hand.

`infra/gcp/` is the live Terraform root: it provisions the GCS bucket (`google_storage_bucket.tft_match_data`), the BigQuery datasets and tables, plus everything to run ingestion as a Cloud Run Job in production (`include/jobs/ingest_matches.py`, image `Dockerfile.jobs`, deps `requirements-jobs.txt`), built by `cloudbuild.yaml` from a Developer Connect trigger and started daily by Cloud Scheduler. See `infra/gcp/README.md`. `main.py` is a placeholder.

## Commands

Airflow runs through the Astro CLI in Docker (`Dockerfile` = Astro Runtime 3.1, Python 3.12 inside the container):
- `astro dev start` / `astro dev restart`: Airflow UI at http://localhost:8080
- `astro dev pytest`: runs `tests/` inside the Airflow container (this is how `pytest.log` was produced)
- `astro dev pytest tests/dags/test_ingest_matches_to_gcs_and_bigquery.py -- -k TestParseMatchData`: run a single test/class
- `astro dev parse`: DAG integrity check (uses `.astro/test_dag_integrity_default.py`, don't edit it)

BigQuery:
- `cd infra/gcp && terraform apply`: create/alter datasets and tables
- `PYTHONPATH=include python -m db.seed_default_data [--skip-embeddings] [--limit N]`: the default dataset. It seeds Set 18 reference data, then loads the matches archived under `tft/matches/16.19.1/2026-09-28/` in GCS. Idempotent, so it doubles as a reset.
- `PYTHONPATH=include python -m jobs.rebuild_stats [--check]`: recompute the totals tables from the match tables, or (with `--check`) report any that disagree with a recount
- `PYTHONPATH=include python -m jobs.cluster_compositions [--patch X] [--dry-run] [--min-cluster-size N]`: cluster a patch's boards into comps (see Compositions below); `--dry-run` prints them and writes nothing
- `PYTHONPATH=include python -m db.seed_reference_data`: only `champions`/`traits`/`items`, from the root `tft-*.json` files (Data Dragon 16.19.1)
- `PYTHONPATH=include python -m jobs.load_gcs_matches --prefix tft/matches/<version>/<date>/ [--reload] [--skip-embeddings]`: load any archived day into BigQuery; skips matches already loaded
- Local runs use Application Default Credentials (`gcloud auth application-default login`); set `GOOGLE_CLOUD_PROJECT`, and `BQ_DATASET` if it isn't `tft`

Supabase (local, frontend only until it moves off): `npx supabase start`, `npx supabase db reset`.

Frontend: `npm run dev` (or `docker compose up`, which uses `Dockerfile.node`), `npm run build`. There is no JS test or lint setup.

Host-side Python uses uv (`pyproject.toml`, Python 3.14, deps in the `dev` group): `uv sync`, `uv run pytest ...`. Note that the tests import Airflow, which is only installed in the Astro container.

## Architecture notes

**Import paths.** DAGs import from `include/` as top-level packages (`from riot_api.match_api import ...`, `from db.parse_match_data import ...`). This works because the `Dockerfile` adds `/usr/local/airflow/include` to `PYTHONPATH` and `pyproject.toml` sets pytest `pythonpath = [".", "include", "dags"]`. Keep using this style, not `include.x`.

**Dependencies live in four places:** `requirements.txt` (Astro/Airflow image), `requirements-jobs.txt` (Cloud Run job image), `pyproject.toml` (uv host env), and `requirements-data.txt` (the Node dev container). Add Airflow-runtime deps to `requirements.txt`, and to `requirements-jobs.txt` too if `include/` code used by the job needs them.

**`ingest_matches_to_gcs_and_bigquery` DAG (daily):**
`collect_match_ids_task.expand(platforms=routing_groups().values())` (one task per routing region) → `collect_matches_task` → fans out to `upload_to_gcs_task` (key `tft/matches/{ddragon_version}/{utc_date}/{match_id}.json`) and `upsert_to_bigquery_task`. `upsert_players_task` runs before the DB upsert. Both DAGs reach BigQuery through `BigQueryHook(gcp_conn_id="google_cloud_default").get_client()`. Tasks are `async` and use `httpx.AsyncClient`. The Riot fetch tasks run with `max_active_tis_per_dagrun=1` to respect rate limits.

**Riot API (`include/riot_api/`).** This is the canonical client. `constants.py` has the regions, the platform→routing map (`RIOT_REGIONS_MAP`) and `HIGH_ELO_TIERS` (Challenger, Grandmaster and Master). Master is ~28k players across `RIOT_REGIONS` and each crawled player costs one sequential match-history request, so `collect_match_ids` crawls per routing region in priority order: every Challenger on the region's platforms, then every Grandmaster (both always in full), then Masters (round-robin by LP rank across the platforms, `MASTER_CRAWL_BATCH` players at a time) until `ROUTING_MATCH_TARGET` (2000) *new* matches are found. It takes a `filter_new` callback (the ingest passes `filter_new_match_ids`) so matches already stored or rejected don't count; `upsert_players` still stores every Master. `collect_match_ids` returns the new matches in priority order as `{match_id: [tiers whose players had it]}`; `TIER_QUEUES` in `constants.py` says which queues a tier may record (ranked 1100 from any tier, normal 1090 only from Challengers, nothing else), and `allowed_queues` takes the union over a match's tiers. League endpoints use the platform (`NA1`), match endpoints use the routing region (`AMERICAS`). Use `riot_get_with_retry` (429/backoff). `riot_data_retrieval.py` is only a re-export shim. `league_api.get_league_entries` returns the full apex-tier list; `include/db/upsert_players.py` builds `players`/`player_ranked_stats` rows straight from it (no per-player calls) and MERGEs them. Riot dev keys expire every 24h, so scheduled runs need a Personal key.

**BigQuery writes (`include/db/bq.py`).** Every writer stages rows into fresh tables in the `tft_staging` dataset with load jobs (free; tables expire after a day), then moves them, and updates the stats counters, with one transaction script, via `run_query`/`with_retry` (retries 5xx and concurrent-DML aborts, with jitter, since parallel tasks MERGE into the same totals rows). Primary and foreign keys are declared `NOT ENFORCED`; the writers keep them true. Every per-match table carries `played_at` and is day-partitioned on it.

**Parsing (`include/db/parse_match_data.py`).** `build_match_rows` is pure apart from the Gemini call: it skips any queue outside its `queues` argument (ranked, `queue_id` 1100, by default) and returns rows keyed by table for `matches`, `players`, `participants` (with a 768-dim `gemini-embedding-001` embedding of the board's units with star level and all items, plus traits, one batched `get_embeddings` call per match), `participant_traits`, `participant_units` (keyed on `slot`, the unit's index on the board, so duplicate champions survive) and `unit_items`. `write_matches` parses a batch and `write_match_rows` replaces those matches in one script: delete `matches` first, delete-then-insert each child table, MERGE `players`, insert `matches` last, so a crash part-way leaves the match absent and it is re-ingested. `filter_new_match_ids` skips already-ingested matches, and matches in `rejected_matches`, before fetching. `select_matches` splits a fetched chunk into the matches to record and the rejected ones (by `allowed_queues` for the tiers that surfaced each); `write_rejected_matches` MERGEs the latter into `rejected_matches` so no later run requests them again, and only the recorded ones are archived to GCS. `build_match_rows`/`write_matches` take a `queues` set (ranked only by default, `INGEST_QUEUES` from the ingest); `load_gcs_matches` stays ranked-only unless `--include-normals`.

**Stats (`include/data_aggregation/` + views).** Stats count ranked matches only (`counts_sql` filters `matches.queue_id = 1100`), since the match tables also hold Challengers' normal games, and so does the comp clustering. Stats are exact integer counters, summed per patch (`patch` is `matches.game_version`), in `patch_totals`, `champion_totals`, `trait_totals`, `item_totals` and `champion_item_totals` (boards, matches, placement sum, top-4 and win counts). `write_match_rows` folds each write's matches into them with one MERGE per table, in the same transaction as the match inserts, so nothing is re-scanned. Each MERGE adds the staged rows' counts and subtracts the rows being replaced, so reloads and overlapping re-ingests never double count, and a match moves patch cleanly. A board counts once per entity however many copies it holds, and only active traits (`tier_current > 0`) count. Rates are never stored: the views `champion_stats`, `trait_stats`, `item_stats` and `champion_item_stats` derive them (`SAFE_DIVIDE`), where `play_rate` is boards per match that had the entity (1 to 8) and `frequency` is boards per match in the patch (0 to 8). `current_*_stats` views (also in `infra/gcp/bigquery/views/`) are the latest patch only, joined to names, and are what LLM and frontend queries should read. The `calculate_tft_stats` DAG has no schedule; it and `python -m jobs.rebuild_stats` rebuild every totals table from the match tables (first backfill, recovery), and `jobs.rebuild_stats --check` diffs the totals against a recount. Reference tables `champions`/`traits`/`items` have no patch column: they are keyed on Riot's api name (e.g. `TFT_Item_BFSword`) and filled by `include/db/seed_reference_data.py`, which upserts and never deletes, so names resolve for old patches. Set 18 api names start with `DA_` (e.g. `DA_18_KhaZix`, `DA_ArchangelsStaff`), which is what the seed filters on; update `TFT_SET`/`SET_ID_PREFIX` and the root `tft-*.json` for a new set.

**Compositions (`include/data_aggregation/compositions.py`).** Boards are grouped into comps from hand-built vectors, not the Gemini embedding (which stays for similarity search). A board's vector has a `u:<champion>` column of `1 + items held` (so carries dominate; duplicate copies take the max) and a `t:<trait>` column of `tier_current` (active traits only), L2-normalised; star levels are not in it. `jobs.cluster_compositions` fits HDBSCAN on a 20k-board sample of the patch (no number of comps to choose), drops clusters whose own boards are not alike (`MIN_COHESION`), then assigns every board to its nearest comp or leaves it out if it is less similar than that comp's boards are. It replaces the patch's rows in `compositions` (exact counters like `*_totals`, plus units, traits and carries as REPEATED records, and a `comp_id` hashed from the core units and carries so it survives reruns) and `participant_compositions`, in one transaction, and writes nothing if no comps are found. It is a separate Cloud Run Job (`tft-cluster-compositions`, same image, daily after the ingest) because it needs the whole patch. `composition_stats` and `current_composition_stats` are the views to read. `dags/cluster_compositions.py` is the unscheduled local equivalent. Tune `--min-cluster-size` with `--dry-run` on real data before trusting the comps.

**Config/secrets.** DAGs read `GEMINI_API_KEY` and `RIOT_API_KEY` (or `API_KEY`) from `.env` (`GEMINI_API_KEY` isn't needed with `SKIP_EMBEDDINGS=1`, which `make_genai_client` honours: ingest then writes boards with no embedding and never calls Gemini. The Cloud Run ingest job sets it by default via the Terraform variable `skip_embeddings`; backfill later with `jobs.load_gcs_matches --reload`), plus optional `BQ_DATASET`/`BQ_STAGING_DATASET` (default `tft`/`tft_staging`). GCS and BigQuery are both accessed through the Airflow connection `google_cloud_default`, defined in `airflow_settings.yaml` (gitignored) with a service account keyfile; that account needs BigQuery Job User on the project and Data Editor on both datasets. The Cloud Run job instead uses its runtime service account's default credentials (granted in `infra/gcp/bigquery.tf`), no key needed.

**Tests.** `tests/conftest.py` points Airflow at a SQLite metadata DB and runs `initdb` once per session. Its `fake_bq` fixture (`FakeBigQuery`) records loads and queries instead of running them and checks every loaded row against the Terraform schema JSON, so a row/table mismatch fails a unit test. `tests/dags/test_constants.py` holds full sample Riot match payloads (ranked and unranked) for parser tests. `tests/dags/test_dag_example.py` asserts that every DAG imports cleanly and has tags and retries.

**CI (`.github/workflows/`).** `lint.yml` runs `ruff check` and `tsc --noEmit`. Ruff is pinned to `0.15.9` (both in the workflow and as a dev dependency) with an explicit `[tool.ruff.lint] select` matching ruff's own conservative defaults (`E4`, `E7`, `E9`, `F`) — without that, a version bump (or `ruff-action` falling back to "latest" when it can't detect a pin) pulls in a much larger ruleset (isort, pylint, flake8-datetimez, ...) this codebase was never written against. `tests.yml` builds the `Dockerfile` image and runs `pytest tests -m "not integration"` inside it, with dummy `GEMINI_API_KEY`/`RIOT_API_KEY` values (the parsing tests patch `get_embeddings` and never call Riot, and BigQuery is faked). Tests marked `@pytest.mark.integration` hit live services and are excluded in CI: `TestCollectMatchIds` (Riot API) and `TestTotalsSqlCompiles` (dry-runs the totals SQL against real BigQuery; run it after `terraform apply`) and `TestBoardsSqlCompiles` (the same for the comps' boards query).
